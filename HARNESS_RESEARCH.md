# Harness interface research

Research date: 24–25 October 2026. Integration targets were selected after inspecting official source and CLI or app interfaces. The UI detects local CLIs and desktop bundles for candidates; detection alone does not imply chat integration.

## OpenAI Codex — implemented and live tested

- Official source: [Codex repository](https://github.com/openai/codex). The [v1 native spawn handler](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/multi_agents/spawn.rs) parses `message`/`items`, computes a prompt preview, emits a `CollabAgentToolCall` start item, calls `agent_control.spawn`, and then emits a completed item with the receiver thread ID. The [v2 spawn handler](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs) parses `message`, calls `thread_spawn::spawn`, then emits `SubAgentActivityItem` with the child ID, model, and path. Its analytics collaboration item explicitly sets `prompt: None`.
- The [exec event projection](https://github.com/openai/codex/blob/main/codex-rs/exec/src/event_processor_with_jsonl_output.rs) maps v1 collaboration items to JSON events. The installed v2 runtime exposed `subAgentActivity` items for native spawn and completion, plus a `collabAgentToolCall` for `wait`; its child thread item list omitted the delegated user prompt. These are observation events. They do not pause or replace the native spawn call.
- [Codex app-server documentation](https://developers.openai.com/codex/app-server) specifies `initialize`, `model/list`, `thread/start`, `thread/resume`, `turn/start`, streamed item notifications, and approval requests. The installed CLI generated a protocol schema matching these methods. It was version `0.163.0-alpha.11` during tests.
- Codex handles its native shell, file, MCP, web, Git, and testing tools. PolyAgent does not implement them. Native Codex threads use the PolyAgent project directory as `cwd`. `model/list` returns a catalog, so connection and model entitlement are not conflated.
- A [reported Codex hook coverage issue](https://github.com/openai/codex/issues/49736) documents that `PreToolUse` was not invoked for `spawn_agent` in version `0.159.2`. Source inspection of the current spawn handler shows no client interception point before `agent_control.spawn`. PolyAgent does not claim redirect support. This limitation is not a claim that every future Codex version has the same behavior.
- Live verification on this machine: app-server authentication succeeded; a read-only inference turn completed; PolyAgent's orchestrator chat completed; a separate subagent chat completed; `thread/items/list` showed its first user message exactly matched the required template; and an Auto Chooser turn returned a model from the discovered catalog. A native Codex subagent spawn completed and PolyAgent recorded the `subAgentActivity` start/completion items with child thread ID and model but no prompt. A bounded fresh-research turn returned three source URLs, one strength, one weakness, and a conclusion. A broader first research prompt timed out and was narrowed; timeouts remain visible failures, not saved findings.

## Google Antigravity — CLI and desktop app live tested

- Official [CLI headless documentation](https://antigravity.google/docs/cli/headless/) specifies `agy models`, persistent `--input-format stream-json --output-format stream-json` sessions, `init` and `result` events, model selection, and `--conversation` resume. The installed 1.4.7 CLI was tested with Gemini; model discovery, authentication, new chat, continuation, resume, and a native delegated task all completed. No Claude model was executed.
- Official [hook documentation](https://antigravity.google/docs/hooks) identifies the native `invoke_subagent` tool and documents `PreToolUse` with tool arguments, `deny`, and `reason`. A real hook received `Prompt`, `Role`, and `TypeName` before the native call. PolyAgent then created a separate Antigravity chat with the exact first message and returned its real answer through the denial reason. The orchestrator used that answer. Hook coverage was tested through both the app and CLI transports.
- The desktop app 2.24.0 runs a local HTTPS language server. Inspection of the installed app’s bundled JavaScript and protobuf descriptors identified the request path for `GetAuthStatus`, `GetAvailableModels`, `CreateProject`, `StartCascade`, `SendUserCascadeMessage`, `WaitForConversationFullyIdle`, and `GetCascadeTrajectory`. Each was exercised against the running app. A native project was created only on first use, and `GetConversationMetadata` confirmed the chat belonged to that project. This is an undocumented, version-sensitive app interface.
- The hook can block a native call and return a reason, but it cannot directly replace the tool result. The native tool therefore records a denial while the orchestrator receives the completed subagent answer in that reason. PolyAgent displays the actual redirected chat and result.

## OpenCode — V2 CLI and native foreground subagent redirection live tested

- Official [V1 server documentation](https://dev.opencode.ai/docs/server/) specifies `opencode serve`, provider discovery, session creation, message and command endpoints, and server events. Official [V2 API documentation](https://dev.opencode.ai/v2/docs/api) specifies `/api/model`, `/api/session`, `/api/session/{id}/prompt`, `/api/session/{id}/message`, and active-session status. PolyAgent calls these HTTP endpoints directly through a CLI-launched local server; it does not use an SDK. V1 code is implemented but was not run against an installed V1 binary.
- The [V2 native subagent implementation](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/subagent.ts) defines `agent`, `description`, `prompt`, optional `sessionID`, model and background fields, creates a child session, prompts it, and returns `{sessionID,status,output}`. The [tool transform documentation](https://dev.opencode.ai/v2/docs/build/plugins/) and [Promise adapter source](https://github.com/anomalyco/opencode/blob/dev/packages/plugin/src/promise/adapter.ts) establish that a project plugin can replace this tool executor and call its original executor for unmanaged sessions. PolyAgent installs such a project plugin only when an OpenCode V2 orchestrator chat is first needed.
- The [V2 session route source](https://github.com/anomalyco/opencode/blob/dev/packages/server/src/handlers/session.ts) shows creation at an explicit directory and prompt admission. The [desktop bundled CLI source](https://github.com/anomalyco/opencode/blob/dev/packages/desktop/src/main/service/desktop-cli.ts) resolves the desktop app's executable from `Contents/Resources/opencode` on macOS. PolyAgent tries the CLI on PATH first, then that bundled executable. A test bundle holding the real binary exercised fallback; no OpenCode desktop app was installed for a live app test.
- The official OpenCode CLI 2.1.4 binary connected on this machine and returned nine available models. A real free-model session answered a prompt. PolyAgent created a separate subagent session, sent the exact first-message template, continued the same session with a direct second message, and received both real responses. A native OpenCode `subagent` call was intercepted before execution; the orchestrator received the child answer. Another native call routed to a fresh Codex chat and returned the Codex answer to OpenCode. A follow-up using the bridge session ID continued the same child chat. A deliberately failing CLI startup fell back to an app-shaped bundle holding the real OpenCode binary. These tests used the CLI runtime; they did not use Claude.
- The V2 plugin deliberately passes background calls through to OpenCode's native tool, preserving their behavior. These calls are observed but not redirected. V1 has no tested replacement plugin path.

## DeepSeek Harness — native CLI Host with agent presets

- The [CLI reference](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/reference/README.md), [native Web CLI](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/src/startup.ts), [session controller](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/api/session-controller/src/index.ts), and [session wire types](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/api/session-controller/src/types.ts) were inspected at commit `22ddee3792402c3e70ec5f86a63c3e3e895a2f60`. The previous ACP path exposes model and reasoning settings but not agent presets. PolyAgent now launches the native CLI Web Host on a private loopback port, exchanges its fresh token for its native cookie, and uses the Host's own unary RPC and WebSocket event interfaces. No harness SDK is used. Catalog discovery no longer creates a probe session.
- The official [desktop README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/desktop/README.md) identifies the app-bundled `resources/runtime/cli/bin/dsh` command. PolyAgent prefers a working PATH CLI and falls back to this bundle when present.
- The [agent preset registry](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset-registry/src/index.ts) exports `agentPresets/list`, marks the effective default, and fixes a preset after a chat has started. [Permission presets](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/interaction/permission-presets/src/index.ts) advertise their catalog and default; the native `/permission` command applies the choice. The app's user configuration lives in its desktop profile patch, so the app fallback passes that file through the CLI's supported `--patch` overlay rather than overwriting the user's native defaults. Native Host discovery and Standard/PTC sessions with selected permission presets have been exercised against the installed app runtime. One inference attempt with the default official provider failed with the provider's invalid-key response; availability is not inferred from model listing alone.
- A subsequent PTC turn through the user's configured provider succeeded. A real native escalation request was forwarded and rejected; the model reported the rejection and stopped. Native `subagent` tool calls are observed from committed session events. The compatibility hook's reduced non-shell arguments still do not provide a reliable redirection contract. No DeepSeek native redirection is claimed.

## Grok Build — CLI and native hook adapter implemented, live turn pending

- The official [CLI reference](https://docs.x.ai/build/cli/reference) and actual [ACP session implementation](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/src/agent/mvp_agent/session_setup.rs) were inspected at commit `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`. PolyAgent uses `grok agent stdio`, native session identities and resume, model config options, native permission requests, and `session/set_mode` for normal/plan/ask behavior. The [permission resolver](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/src/session/auto_mode.rs) reads `_meta.yoloMode` and `_meta.autoMode`; absent fields preserve native configuration. The former hardcoded `--always-approve` behavior has been removed.
- The native [task input source](https://github.com/xai-org/grok-build/blob/main/crates/common/xai-tool-types/src/task.rs) carries the full `prompt`, and the [tool source](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/mod.rs) accepts `task`, `Task`, and `spawn_subagent` as native tool names. Official [hook documentation](https://docs.x.ai/build/features/hooks) says project `PreToolUse` hooks receive `toolName`, `toolInput`, `sessionId`, and `cwd`, and can block the tool. The [hook parser](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-hooks/src/runner/mod.rs) clips a denial reason to 256 characters. PolyAgent therefore installs a project hook for only those names, starts a new selected-harness subagent chat, blocks the native task, and sends the full response as a continuation in the same Grok session. It leaves ordinary tools and native worktree or resumed-child calls alone. Project hook trust is granted through Grok's native `--trust` flag when its orchestrator starts.
- Grok Build is not installed on this machine. The implementation follows its source and published CLI contract; actual authentication, turns, and hook interception remain untested here. No Grok desktop app control interface was found, so the integration targets its CLI.

## Chat and mode changes — October 26, 2026

- Codex: inspected [thread parameters](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs), [turn parameters](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/turn.rs), and permission types at commit `970111f6cb62cc02fe36a82ea7d71b37a2889c97`. Native approval and sandbox overrides are optional. Plan/default collaboration modes require `experimentalApi` at initialization, confirmed by a real server refusal and successful run after adding that capability. Two real threads in one PolyAgent project returned separate tokens; continuing the first recalled its own token and kept the same native thread. User messages, answers, and subagent events carry their conversation identity.
- OpenCode: inspected [session routes](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/session.ts), [permission routes](https://github.com/anomalyco/opencode/blob/dev/packages/protocol/src/groups/permission.ts), [permission schema](https://github.com/anomalyco/opencode/blob/dev/packages/schema/src/permission.ts), and execution handlers at commit `f7a9f1bf06971ef20d95cf83cf1309cc985090ac`. V2 uses `permissions: [{action, resource, effect}]`, native agent IDs, per-session pending permissions, and `decision: once|always|reject`. V1 uses its own published rule/reply shapes. These mode changes are source-inspected; OpenCode is not installed for a live run here.
- Antigravity: official [CLI modes](https://www.antigravity.google/docs/cli/modes/) and [CLI settings](https://www.antigravity.google/docs/cli/reference/) document `--mode`, persisted `toolPermission`, and `--dangerously-skip-permissions`. No public app source repository is available. The running app's compiled `main.js` and embedded protobuf descriptors were inspected directly: native `CascadeConfig.plannerConfig.toolConfig.runCommand.autoCommandConfig.autoExecutionPolicy` values are OFF=1, AUTO=2, EAGER=3, PROCEED_IN_SANDBOX=4; artifact review values are ALWAYS=1, TURBO=2, AUTO=3. `HandleCascadeUserInteraction` accepts one-time native approval responses tied to trajectory and step. A real app turn succeeded with Request Review applied. Inheriting settings omits these overrides. App execution mode choices not exposed by this transport are not invented.
- Settings are stored separately from model-selection modes. A user's last selected harness modes seed new chats; each existing conversation keeps its own values. The native default choice omits overrides. DeepSeek preset changes require a new chat because its native registry enforces that constraint. Local tests cover lazy chat creation, persistent isolation, legacy history migration, cross-project rejection, mode persistence, native-default omission, and frontend conversation filtering.

## Harness-specific controls follow-up — October 26, 2026

Rechecked the actual DeepSeek [permission catalog types](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/interaction/permission-presets/src/types.ts), [permission implementation](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/interaction/permission-presets/src/index.ts), and [agent registry](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/preset/agent-preset-registry/src/index.ts). Native `name` and `description` fields now reach the controls without replacing their values. The derived `custom` permission remains display-only and is not offered as a switch target. Rechecked Grok's [permission resolver](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/src/session/auto_mode.rs), which gates Auto on native feature support. Antigravity's [CLI mode documentation](https://www.antigravity.google/docs/cli/modes/) and [app artifact review documentation](https://www.antigravity.google/docs/artifact-review/) distinguish execution modes, tool policy, and artifact review. The previously inspected app protobuf fields are now set independently for terminal execution and artifact review. Local transport-contract tests confirm that selecting either policy omits the other field when inheriting it. This follow-up did not run inference in Grok or OpenCode or test Claude.

## Local discovery and fallback verification

PolyAgent checks CLI commands on PATH with `--version`, then inspects macOS app bundles without launching them. Codex uses its working CLI first and retries the app-bundled runtime when the CLI is missing or fails. Antigravity uses a working authenticated `agy` CLI first and falls back to the running desktop app when CLI discovery or connection fails. OpenCode starts the CLI server from PATH first and falls back to the desktop app's bundled CLI when present. Real tests covered Antigravity CLI preference with both installed, missing CLI to app, and a deliberately failing CLI to app. The app fallback discovered 15 usable agent models; CLI 1.4.7 discovered six. An OpenCode app-shaped bundle with the real CLI confirmed the fallback branch and discovered nine models, though an actual OpenCode app was not installed. Model catalog entries still require a successful turn to verify task access.

Antigravity manual delegation was tested end to end through both CLI and app. An Antigravity app native call was also redirected to a fresh Codex chat; Codex completed the task and its answer returned to the Antigravity orchestrator. The app path also verified the exact first message, a direct second message in the same subagent chat, native project association, and Ask Every Time model selection. Full Auto chooser evaluation was tested with Gemini through both transports. An Antigravity app research turn returned three cited evidence records and saved them locally. The uninstalled candidate harnesses were not represented as working integrations. Claude was not tested after the user revoked its subscription.
